  <name>Task 1: Update gateway workflow with workflow_dispatch and custom domain health check</name>
  <files>.github/workflows/gateway.yml</files>
  <action>
Update `.github/workflows/gateway.yml` with two changes:

**1. Add `workflow_dispatch` trigger** (per user decision: manual re-deploy available without code push):

Update the `on:` section to include `workflow_dispatch:` at the same level as `push:`. The workflow_dispatch enables manual re-deployment via the GitHub Actions UI.

```yaml
on:
  push:
    branches: [main]
    paths:
      - "apps/gateway/**"
      - "packages/**"
      - "connectors/**"
    tags:
      - "v*"
  workflow_dispatch:
```

Note: `workflow_dispatch` triggers run on the default branch. The `deploy-staging` job's `if: github.ref == 'refs/heads/main'` condition already covers this correctly — manual dispatch from main will trigger staging deploy.

**2. Update staging health check URL** from workers.dev to custom domain:

Change the smoke test URL from:
```yaml
url: https://feelr-gateway-staging.feelr.workers.dev/health
```
To:
```yaml
url: https://staging-api.feelr.dev/health
```

This is important because `workers_dev = false` in wrangler.toml (from Plan 01) means the workers.dev URL will no longer be available. The health check must use the custom domain. The `/health` endpoint is exempt from CF Access via Bypass policy, so no auth headers needed.
  </action>

  </verify>

**Dashboard workflow (`.github/workflows/dashboard.yml`):**

Update the `deploy-staging` job with these changes:

1. **Change staging gateway URL** in the build step env:
   - From: `NEXT_PUBLIC_GATEWAY_URL: https://feelr-gateway-staging.feelr.workers.dev`
   - To: `NEXT_PUBLIC_GATEWAY_URL: https://staging-api.feelr.dev`
   - This ensures the staging dashboard connects to the staging gateway via its custom domain (per STAGE-04 requirement and Pitfall 4 from research).

2. **Change SWA deployment token** to use the staging-specific secret:
   - From: `azure_static_web_apps_api_token: ${{ secrets.SWA_DASHBOARD_DEPLOYMENT_TOKEN }}`
   - To: `azure_static_web_apps_api_token: ${{ secrets.SWA_DASHBOARD_STAGING_TOKEN }}`
   - This deploys to the separate staging SWA instance, NOT the production instance's staging environment.

3. **Remove `deployment_environment: staging`** line entirely from the SWA deploy step.
   - The staging SWA instance IS the production slot of a separate SWA resource. There is no named environment needed — omitting `deployment_environment` deploys to the default (production) slot of the staging instance.

4. **Add health check step** after the SWA deploy step:
   ```yaml
   - name: Smoke test staging dashboard
     uses: jtalk/url-health-check-action@v4
     with:
       url: https://staging-app.feelr.dev/health
       max-attempts: 3
       retry-delay: 5s
   ```

**Docs workflow (`.github/workflows/docs.yml`):**

Same pattern of changes for the `deploy-staging` job:

1. **Change SWA deployment token:**
   - From: `azure_static_web_apps_api_token: ${{ secrets.SWA_DOCS_DEPLOYMENT_TOKEN }}`
   - To: `azure_static_web_apps_api_token: ${{ secrets.SWA_DOCS_STAGING_TOKEN }}`

2. **Remove `deployment_environment: staging`** line entirely.

3. **Add health check step** after the SWA deploy step:
   ```yaml
   - name: Smoke test staging docs
     uses: jtalk/url-health-check-action@v4
     with:
       url: https://staging-docs.feelr.dev/health
       max-attempts: 3
       retry-delay: 5s
   ```

Note: Docs has no gateway URL env var (pure content site — no change needed there).

Both workflows already have `workflow_dispatch:` in their triggers, so no change needed for that.
  </action>
