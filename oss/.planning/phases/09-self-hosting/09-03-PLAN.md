These DOs replace Cloudflare KV and D1 for self-hosted mode. They use workerd's native DO SQL storage (`this.ctx.storage.sql`), the same mechanism the existing TokenCoordinator uses.

**KvStoreDO** (`self-hosted/kv-store-do.ts`):

A Durable Object that implements a key-value store using its built-in SQLite storage. Import `DurableObject` from `cloudflare:workers`.

Constructor: `blockConcurrencyWhile` to create the schema:
```sql
CREATE TABLE IF NOT EXISTS kv (
  key TEXT PRIMARY KEY,
  value TEXT NOT NULL
)
```

RPC methods matching `KeyValueStore` interface (called via DO stub from the adapter wrapper):
- `async kvGet(key: string): Promise<string | null>` -- SELECT value FROM kv WHERE key = ?
- `async kvGetJson<T>(key: string): Promise<T | null>` -- same but JSON.parse the result
- `async kvPut(key: string, value: string): Promise<void>` -- INSERT OR REPLACE
- `async kvDelete(key: string): Promise<void>` -- DELETE FROM kv WHERE key = ?
- `async kvList(prefix?: string): Promise<{ keys: Array<{ name: string }> }>` -- SELECT key FROM kv WHERE key LIKE ? (prefix + '%') or SELECT key FROM kv if no prefix

Note: Method names prefixed with `kv` to avoid conflicts with DO base class methods. The adapter wrapper (created in Plan 05's factory) translates KeyValueStore method names to these RPC names.

Follow the same pattern as TokenCoordinator: extend `DurableObject`, use `this.ctx.storage.sql.exec()` for queries, convert `.toArray()` for row results.

**UsageDbDO** (`self-hosted/usage-db-do.ts`):

A Durable Object that implements a SQL database using its built-in SQLite storage. This replaces D1 for usage analytics.

Constructor: `blockConcurrencyWhile` to create tables (same schemas from usage-recorder.ts):
```sql
CREATE TABLE IF NOT EXISTS usage (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  api_key_short TEXT NOT NULL,
  connector TEXT NOT NULL,
  action TEXT NOT NULL,
  status_code INTEGER NOT NULL,
  duration_ms INTEGER NOT NULL,
  timestamp TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_usage_api_key_short ON usage(api_key_short);
CREATE INDEX IF NOT EXISTS idx_usage_connector ON usage(connector);
CREATE INDEX IF NOT EXISTS idx_usage_timestamp ON usage(timestamp);
CREATE INDEX IF NOT EXISTS idx_usage_key_connector ON usage(api_key_short, connector);

CREATE TABLE IF NOT EXISTS rate_limit_events (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  api_key_short TEXT NOT NULL,
  tier TEXT NOT NULL,
  ip TEXT NOT NULL,
  timestamp TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_rle_api_key_short ON rate_limit_events(api_key_short);
CREATE INDEX IF NOT EXISTS idx_rle_timestamp ON rate_limit_events(timestamp);
```

RPC methods for SQL execution:
- `async query<T>(sql: string, ...binds: unknown[]): Promise<{ results: T[] }>` -- executes SQL with binds, returns results array. Uses `this.ctx.storage.sql.exec(sql, ...binds).toArray()`.
- `async queryFirst<T>(sql: string, ...binds: unknown[]): Promise<T | null>` -- same but returns first row or null
- `async execute(sql: string, ...binds: unknown[]): Promise<{ meta: { changes?: number } }>` -- for INSERT/UPDATE/DELETE. Uses `this.ctx.storage.sql.exec(sql, ...binds)` and returns `{ meta: { changes: this.ctx.storage.sql.exec("SELECT changes() as c").one().c } }`.

Note on `datetime('now', ...)`: workerd's SQLite supports `datetime()` function natively. The existing D1 queries using `datetime('now', '-24 hours')` will work as-is in DO SQLite.

Note on `strftime()`: Also supported natively in DO SQLite.

Env type for both DOs can be empty `{}` since they don't need external bindings.

Create `InMemoryRateLimiter` that implements the `RateLimiter` interface using an in-memory sliding window algorithm.

```typescript
import type { RateLimiter } from '../interfaces'

export class InMemoryRateLimiter implements RateLimiter {
  private windows = new Map<string, number[]>()
  private readonly maxRequests: number
  private readonly windowMs: number

  constructor(maxRequests: number, windowSeconds: number) {
    this.maxRequests = maxRequests
    this.windowMs = windowSeconds * 1000

    // Periodic cleanup of expired entries to prevent memory leak
    // Run every 60 seconds, remove entries older than 2x window
    setInterval(() => this.cleanup(), 60_000)
  }

  async limit(options: { key: string }): Promise<{ success: boolean }> {
    const now = Date.now()
    const key = options.key
    const timestamps = this.windows.get(key) ?? []

    // Remove expired entries outside the window
    const valid = timestamps.filter(t => now - t < this.windowMs)

    if (valid.length >= this.maxRequests) {
      this.windows.set(key, valid)
      return { success: false }
    }

    valid.push(now)
    this.windows.set(key, valid)
    return { success: true }
  }

  private cleanup(): void {
    const now = Date.now()
    const cutoff = this.windowMs * 2
    for (const [key, timestamps] of this.windows) {
      const valid = timestamps.filter(t => now - t < cutoff)
      if (valid.length === 0) {
        this.windows.delete(key)
      } else {
        this.windows.set(key, valid)
      }
    }
  }
}
```

Key design points:
- For self-hosted single-instance deployments, in-memory rate limiting is actually MORE accurate than Cloudflare's per-location distributed limits
- Periodic cleanup prevents unbounded memory growth from abandoned keys
- Async interface matches RateLimiter (even though implementation is synchronous)
- Constructor takes configurable limit and window (matches feelr.yaml rate_limits config)

Note: `setInterval` works in workerd (it's a Web Standard API). The interval is long (60s) so it doesn't impact performance.
