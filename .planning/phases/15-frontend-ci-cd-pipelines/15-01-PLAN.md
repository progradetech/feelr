  <name>Task 1: Set GitHub Actions secrets for SWA deployment tokens</name>
  <action>
    The SWA deployment tokens from Phase 14 must be stored as GitHub Actions repository secrets before the dashboard and docs workflows (Plan 02) can deploy.

    Retrieve the tokens and set them:

    ```bash
    # Retrieve dashboard deployment token
    DASHBOARD_TOKEN=$(az staticwebapp secrets list \
      --name feelr-dashboard \
      --resource-group feelr-rg \
      --query "properties.apiKey" -o tsv)

    # Retrieve docs deployment token
    DOCS_TOKEN=$(az staticwebapp secrets list \
      --name feelr-docs \
      --resource-group feelr-rg \
      --query "properties.apiKey" -o tsv)

    # Set as GitHub Actions secrets
    gh secret set SWA_DASHBOARD_DEPLOYMENT_TOKEN --body "$DASHBOARD_TOKEN"
    gh secret set SWA_DOCS_DEPLOYMENT_TOKEN --body "$DOCS_TOKEN"
    ```

    If `gh` is not authenticated, set secrets via GitHub web UI:
    1. Go to https://github.com/andrewprograde/feelr/settings/secrets/actions
    2. Add SWA_DASHBOARD_DEPLOYMENT_TOKEN with the dashboard token value
    3. Add SWA_DOCS_DEPLOYMENT_TOKEN with the docs token value
  </action>
  <verify>
    Run `gh secret list` and confirm both SWA_DASHBOARD_DEPLOYMENT_TOKEN and SWA_DOCS_DEPLOYMENT_TOKEN appear in the output.
    If gh is not available, verify via GitHub web UI at Settings > Secrets and variables > Actions.
  </verify>
  <done>Both SWA deployment token secrets are configured in the GitHub repository and available to workflows.</done>

  <action>
    **Part A: Update turbo.json**

    Add `NEXT_PUBLIC_GATEWAY_URL` to the build task's `env` array in turbo.json. This ensures Turborepo includes the env var value in its hash, preventing cache hits across staging/production builds with different gateway URLs. The updated build task should look like:

    ```json
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**", "out/**"],
      "env": ["NEXT_PUBLIC_GATEWAY_URL"]
    }
    ```

    **Part B: Create gateway.yml (consolidation)**

    Create `.github/workflows/gateway.yml` that combines the content from `deploy-staging.yml` and `deploy-production.yml` into a single workflow with two jobs.

    Structure:
    - `name: Gateway`
    - Trigger: `on.push.branches: [main]` with paths (`apps/gateway/**`, `packages/**`, `connectors/**`) + `on.push.tags: ["v*"]`
    - Job `deploy-staging`: Conditional on `github.ref == 'refs/heads/main'`, uses `deploy-staging` concurrency group (unchanged -- still shared with ci.yml gateway-preview), contains the wrangler deploy --env staging step and smoke test. Exact same steps as current deploy-staging.yml.
    - Job `deploy-production`: Conditional on `startsWith(github.ref, 'refs/tags/v')`, uses `deploy-production` concurrency group, has `environment: production`, contains the full gradual rollout (versions upload -> 10% -> smoke test -> 100%). Exact same steps as current deploy-production.yml.

    IMPORTANT: The `paths` filter only applies to branch pushes, NOT tag pushes. Tag pushes will always trigger the workflow regardless of paths. The `if:` conditions on each job handle the gating correctly.

    IMPORTANT: Preserve the exact deploy-staging concurrency group name `deploy-staging` (not `deploy-gateway-staging`). This name is shared with ci.yml's gateway-preview job per Phase 13 decision.

    Preserve the DO migration note from deploy-production.yml as a comment at the top of the workflow.

    **Part C: Delete old workflow files**

    Delete `.github/workflows/deploy-staging.yml` and `.github/workflows/deploy-production.yml` after creating `gateway.yml`. Use `git rm` to track the deletion.
