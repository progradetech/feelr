  <name>Task 1: Add staging custom domain route and disable workers.dev</name>
  <files>apps/gateway/wrangler.toml</files>
  <action>
In `apps/gateway/wrangler.toml`, update the `[env.staging]` section:

1. Change `workers_dev = true` to `workers_dev = false` — disables the `.workers.dev` URL so all staging traffic routes through the custom domain (and thus through CF Access). The workers.dev URL would be an unprotected backdoor if left enabled.

2. Add the custom domain route AFTER the `[env.staging]` line and `workers_dev` line, but BEFORE `[env.staging.vars]`:

```toml
[[env.staging.routes]]
pattern = "staging-api.feelr.dev"
custom_domain = true
```

3. Update the comment block above `[env.staging]` to reflect the new access URL:
   - Change `# Access: https://feelr-gateway-staging.<subdomain>.workers.dev` to `# Access: https://staging-api.feelr.dev`

Cloudflare auto-creates the DNS record when `custom_domain = true` is set. No manual CNAME creation needed for the gateway. The DNS record is automatically proxied, so CF Access works immediately.
  </action>
  <verify>
Verify the file has:
- `workers_dev = false` under `[env.staging]`
- `[[env.staging.routes]]` with `pattern = "staging-api.feelr.dev"` and `custom_domain = true`
- Updated comment showing the new staging URL
  </verify>
  <done>wrangler.toml staging section has custom domain route pointing to staging-api.feelr.dev with workers_dev disabled</done>

<task type="auto">
  <name>Task 2: Add verbose error responses for staging environment</name>
  <files>apps/gateway/src/middleware/error-handler.ts</files>
  <action>
Modify `apps/gateway/src/middleware/error-handler.ts` to include verbose error details when `ENVIRONMENT === 'staging'`. The `ENVIRONMENT` binding is already available in `c.env` (defined in AppEnv types.ts, set to "staging" in wrangler.toml vars). The `wrapError` function already supports an optional `detail` field.

Add an `isStaging` constant at the top of the error handler function:
```typescript
const isStaging = c.env.ENVIRONMENT === 'staging';
```

Then update three error cases:

1. **FeelrError block** — no change needed. FeelrErrors already pass through their `detail` field. These are intentional error messages, not sensitive.

2. **HTTPException block** — the current code already passes `err.message` as `detail`. Update the `message` field to be verbose in staging:
   - `message: isStaging ? err.message : 'An unexpected error occurred'`
   - Keep `detail: isStaging ? \`HTTPException: ${err.message}\` : undefined` (only show detail in staging, hide in production)

3. **Unknown error block** — this currently has NO detail field. Add verbose information in staging:
   - `message: isStaging && err instanceof Error ? err.message : 'An unexpected error occurred'`
   - `detail: isStaging && err instanceof Error ? err.stack : undefined`

This gives staging developers the full error message and stack trace for debugging, while production returns the generic "An unexpected error occurred" message with no stack trace exposure.
  </action>
  <verify>
Read the updated file and verify:
- `const isStaging = c.env.ENVIRONMENT === 'staging'` exists near the top of the handler
- HTTPException block uses conditional message and detail based on isStaging
- Unknown error block includes err.message and err.stack in staging, generic message in production
- FeelrError block is unchanged
  </verify>
  <done>Error handler returns verbose error details (message + stack) in staging environment and generic messages in production</done>
</task>
