<task type="checkpoint:human-action" gate="blocking">
  <name>Task 1: Provision Azure SWA staging instances, DNS, CF Access, and GitHub secrets</name>
  <action>
The following manual steps must be completed in order. These CANNOT be automated because they require Azure Portal, Cloudflare Dashboard, and GitHub web UI access with credentials Claude does not have.

**Step 1: Create Azure SWA staging instances (Azure Portal)**

Create TWO new Azure Static Web App resources (Standard plan, $9/mo each):

| Instance Name | Resource Group | Plan | Deployment Source |
|---------------|---------------|------|-------------------|
| `feelr-dashboard-staging` | (same as production SWA) | Standard | Other (GitHub Actions) |
| `feelr-docs-staging` | (same as production SWA) | Standard | Other (GitHub Actions) |

For each: Azure Portal → Static Web Apps → Create → select "Other" deployment source → Standard plan.

After creation, note:
- Each instance's **default hostname** (format: `<name>-<hash>.<region>.azurestaticapps.net`)
- Each instance's **deployment token** (Settings → Manage deployment token → copy)

**Step 2: Set GitHub Actions secrets (GitHub web UI)**

Go to: github.com/progradetech/feelr → Settings → Secrets and variables → Actions → Repository secrets

Add TWO new secrets:
- `SWA_DASHBOARD_STAGING_TOKEN` → paste dashboard staging deployment token
- `SWA_DOCS_STAGING_TOKEN` → paste docs staging deployment token

**Step 3: Configure DNS records (Cloudflare Dashboard)**

Go to: Cloudflare Dashboard → feelr.dev zone → DNS → Records

Add these records for dashboard staging:

| Type | Name | Value | Proxy |
|------|------|-------|-------|
| TXT | `_dnsauth.staging-app` | (Azure validation token from Portal — see Step 4) | N/A |
| CNAME | `staging-app` | `<dashboard-staging-hostname>.azurestaticapps.net` | DNS only (gray cloud) initially |

Add these records for docs staging:

| Type | Name | Value | Proxy |
|------|------|-------|-------|
| TXT | `_dnsauth.staging-docs` | (Azure validation token from Portal — see Step 4) | N/A |
| CNAME | `staging-docs` | `<docs-staging-hostname>.azurestaticapps.net` | DNS only (gray cloud) initially |

Note: The gateway DNS record (`staging-api`) is auto-created by Cloudflare when the gateway is deployed with `custom_domain = true`. No manual DNS setup needed for gateway.

**Step 4: Add custom domains in Azure Portal**

For each SWA staging instance:
1. Go to: Azure Portal → Static Web App → Custom domains → Add
2. Enter the custom domain (`staging-app.feelr.dev` or `staging-docs.feelr.dev`)
3. Azure shows a validation token — use this as the TXT record value in Step 3
4. Wait for validation to succeed (usually 1-5 minutes)

**Step 5: Switch CNAME to Proxied (Cloudflare Dashboard)**

After BOTH Azure custom domain validations succeed:
1. Go back to Cloudflare DNS
2. Edit `staging-app` CNAME → toggle Proxy status to "Proxied" (orange cloud)
3. Edit `staging-docs` CNAME → toggle Proxy status to "Proxied" (orange cloud)

IMPORTANT: Keep the `_dnsauth.staging-app` and `_dnsauth.staging-docs` TXT records permanently — Azure uses them for 6-month certificate renewals.

**Step 6: Configure CF Access (Cloudflare Zero Trust Dashboard)**

Go to: one.dash.cloudflare.com → Access → Applications

Create SIX applications (main + health bypass for each staging subdomain):

**Gateway main:**
- Name: "Feelr Staging API"
- Domain: `staging-api.feelr.dev`
- Policy name: "Allow team"
- Policy action: Allow
- Include rule: Emails — add allowed email addresses
- Authentication: One-time PIN

**Gateway health bypass:**
- Name: "Feelr Staging API Health"
- Domain: `staging-api.feelr.dev`
- Path: `health`
- Policy name: "Public health"
- Policy action: Bypass
- Include rule: Everyone

Repeat the same pair (main + health bypass) for:
- `staging-app.feelr.dev` (Dashboard)
- `staging-docs.feelr.dev` (Docs)

Note: CF Access evaluates the most-specific path first, so the `/health` bypass takes precedence over the domain-level Allow policy.

**Step 7: Trigger deployment**

Push the code changes from Plans 01-03 to main (or trigger workflow_dispatch on all three workflows) to deploy to the new staging infrastructure.
