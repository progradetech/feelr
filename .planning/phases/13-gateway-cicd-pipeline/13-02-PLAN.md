    The concurrency group `deploy-staging` is the SAME group used by the ci.yml gateway-preview job. This ensures PR preview deploys and main-branch deploys never race (Pitfall 4 from research).

    Path filters ensure only gateway-related changes trigger a deploy -- changes to docs, dashboard, or CLI code are ignored.

<task type="auto">
  <name>Task 2: Create production deployment workflow with gradual rollout and approval gate</name>
  <files>.github/workflows/deploy-production.yml</files>
  <action>
    Create `.github/workflows/deploy-production.yml`:

    **Trigger:** `push` tags matching `v*` (same pattern as release.yml -- both run independently on the same tag)

    **Concurrency:** group `deploy-production`, cancel-in-progress: false

    **Single job: `deploy`**
    - runs-on: ubuntu-latest
    - timeout-minutes: 20
    - environment: production (triggers GitHub environment approval gate -- CI-07)
    - Steps:
      1. `actions/checkout@v4`
      2. `pnpm/action-setup@v4`
      3. `actions/setup-node@v4` with node-version 20, cache pnpm
      4. `pnpm install --frozen-lockfile`
      5. Upload new version (without deploying): `cloudflare/wrangler-action@v3` with `command: versions upload --env production --tag ${{ github.ref_name }} --message "Release ${{ github.ref_name }}"`, `workingDirectory: apps/gateway`, `packageManager: pnpm`
      6. Get version ID: run step that executes `npx wrangler versions list --env production --json | jq -r '.[0].id'` and sets output `version_id` via GITHUB_OUTPUT. Set working-directory to apps/gateway and env vars CLOUDFLARE_API_TOKEN + CLOUDFLARE_ACCOUNT_ID.
      7. Gradual deploy at 10%: `cloudflare/wrangler-action@v3` with `command: versions deploy ${{ steps.version.outputs.version_id }}@10% --env production --yes --message "Canary ${{ github.ref_name }} at 10%"`
      8. Smoke test at 10%: `jtalk/url-health-check-action@v4` with url `https://api.feelr.dev/health`, max-attempts 5, retry-delay 10s (more retries for production -- traffic only hits new version 10% of the time)
      9. Full deploy at 100%: `cloudflare/wrangler-action@v3` with `command: versions deploy ${{ steps.version.outputs.version_id }}@100% --env production --yes --message "Release ${{ github.ref_name }} at 100%"`

    Key design decisions:
    - Uses `versions upload` + `versions deploy` (NOT `wrangler deploy`) to enable gradual rollout (GW-05)
    - The 10% -> smoke test -> 100% flow is automatic. For manual percentage control, a developer can use `wrangler versions deploy` directly via CLI.
    - If the Worker has new DO migrations (`[[migrations]]` changes), `versions upload` will fail. The developer must use `wrangler deploy --env production` manually for migration releases. This is a known, documented constraint (Pitfall 2).
    - `environment: production` requires GitHub environment protection rules to be configured. If not configured, the job runs without an approval gate -- it still works, just without the gate.
    - Both release.yml (GoReleaser CLI) and deploy-production.yml run on v* tags. They are independent workflows with different concurrency groups.
  </action>
  <verify>
    Verify YAML validity: `python3 -c "import yaml; yaml.safe_load(open('.github/workflows/deploy-production.yml'))"`.
    Verify the file contains: tag trigger v*, environment production, concurrency group deploy-production, versions upload, versions deploy at 10%, smoke test, versions deploy at 100%.
  </verify>
  <done>deploy-production.yml exists with v* tag trigger, GitHub environment approval gate, gradual rollout (versions upload -> 10% deploy -> smoke test -> 100% deploy), and concurrency controls.</done>
