<task type="auto">
  <name>Task 1: Provision Cloudflare resources and update wrangler.toml with real IDs</name>
  <files>apps/gateway/wrangler.toml</files>
  <action>
All commands run from `apps/gateway/` directory.

**Step 1: Verify Wrangler authentication**
```bash
npx wrangler whoami
```
If not authenticated, this will fail and an auth gate should be created (run `npx wrangler login`).

**Step 2: Create KV namespaces**
```bash
npx wrangler kv namespace create AUTH_KV --env staging
# Capture the `id` from output

npx wrangler kv namespace create AUTH_KV --env production
# Capture the `id` from output
```

**Step 3: Create D1 databases**
```bash
npx wrangler d1 create feelr-usage-staging
# Capture the `database_id` from output

npx wrangler d1 create feelr-usage-production
# Capture the `database_id` from output
```

**Step 4: Replace placeholder IDs in wrangler.toml**
Using the IDs captured from commands above, replace these exact strings in `apps/gateway/wrangler.toml`:
- `PLACEHOLDER_STAGING_KV` -> real staging KV ID
- `PLACEHOLDER_STAGING_D1` -> real staging D1 database_id
- `PLACEHOLDER_PRODUCTION_KV` -> real production KV ID
- `PLACEHOLDER_PRODUCTION_D1` -> real production D1 database_id

**Step 5: Deploy staging Worker (creates feelr-gateway-staging)**
```bash
npx wrangler deploy --env staging
```
This will fail on first health check (no secrets yet) but the Worker will exist.

**Step 6: Deploy production Worker (creates feelr-gateway-production)**
```bash
npx wrangler deploy --env production
```
This also creates the Custom Domain for `api.feelr.dev` (auto-DNS record + Advanced Certificate).

**Step 7: Apply D1 migrations to both databases**
```bash
npx wrangler d1 migrations apply feelr-usage-staging --env staging --remote
npx wrangler d1 migrations apply feelr-usage-production --env production --remote
```
This creates the `usage` and `rate_limit_events` tables from `0001_init.sql`.

**Important notes:**
- If `wrangler kv namespace create` or `wrangler d1 create` fails with auth errors, create an auth gate checkpoint for the user.
- The D1 migration files must exist at `apps/gateway/migrations/0001_init.sql` (created by Plan 12-01).
- The `--remote` flag on `d1 migrations apply` is critical -- without it, the migration only applies to local SQLite.
  </action>

  <how-to-verify>
1. **Staging health check** -- Verify staging Worker responds:
   ```bash
   curl -s https://feelr-gateway-staging.YOUR_SUBDOMAIN.workers.dev/health
   ```
   Expected: 200 OK with health response.

2. **Production health check via Custom Domain** -- Verify api.feelr.dev works with valid SSL:
   ```bash
   curl -sI https://api.feelr.dev/health
   ```
   Expected: HTTP/2 200 with `cf-ray` header (proves Cloudflare is serving it). The `.dev` TLD enforces HTTPS via HSTS preload.

3. **SSL certificate** -- Verify valid certificate:
   ```bash
   curl -sv https://api.feelr.dev/health 2>&1 | grep "subject:"
   ```
   Expected: Certificate issued for `api.feelr.dev` by Cloudflare.

4. **DNS resolution** -- Verify api.feelr.dev resolves:
   ```bash
   dig api.feelr.dev @1.1.1.1 +short
   ```
   Expected: Returns Cloudflare IP addresses.

5. **Data isolation** -- Write a test key to staging KV and confirm it does NOT appear in production:
   ```bash
   npx wrangler kv key put --env staging --binding AUTH_KV "isolation-test" "staging-only"
   npx wrangler kv key get --env production --binding AUTH_KV "isolation-test"
   ```
   Expected: Production returns "Key not found" or similar error.

6. **Secret preservation** -- Redeploy staging (no code changes) and verify secrets are still set:
   ```bash
   cd apps/gateway && npx wrangler deploy --env staging
   curl -s https://feelr-gateway-staging.YOUR_SUBDOMAIN.workers.dev/health
   ```
   Expected: Still returns 200 (secrets preserved across deploy).

Clean up isolation test key:
```bash
npx wrangler kv key delete --env staging --binding AUTH_KV "isolation-test"
```
