Create 5 shell scripts in `scripts/`. All scripts use `#!/usr/bin/env bash` with `set -euo pipefail`. Follow the style of `self-host/init.sh` for color output helpers (info, success, warn, error functions using ANSI escape codes). Each script must:

1. Start with a header comment block: purpose, usage, and a prominent warning that CI/CD is the primary deployment mechanism
2. Define color output helpers (info/success/warn/error)
3. Validate required tools are installed (check for wrangler, az, pnpm etc.)
4. Include confirmation prompts before destructive operations (production deploys, rollbacks)
5. Have extensive inline comments explaining WHAT each step does and WHY

**scripts/deploy-gateway-staging.sh:**
- Purpose: Deploy gateway to staging environment
- Steps: pnpm install -> wrangler deploy --env staging -> health check
- Health check: curl the staging URL and verify 200 response
- Working directory: must cd to `apps/gateway` or use `--config` flag

**scripts/deploy-gateway-production.sh:**
- Purpose: Deploy gateway to production with gradual rollout (mirrors gateway.yml)
- Steps: pnpm install -> versions upload --env production -> extract version ID -> versions deploy at 10% -> health check -> versions deploy at 100%
- Require explicit confirmation before starting ("This will deploy to PRODUCTION. Type 'yes' to continue:")
- Include `--tag` and `--message` flags using git tag if available
- Add a note about DO migration constraint: if wrangler.toml has new [[migrations]], user must use `wrangler deploy --env production` directly instead

**scripts/deploy-dashboard.sh:**
- Purpose: Deploy dashboard to Azure SWA
- Accept `--env staging|production` argument (default: staging)
- Steps: pnpm install -> set NEXT_PUBLIC_GATEWAY_URL based on env -> turbo build --filter=@feelr/dashboard -> copy staticwebapp.config.json to out/ -> deploy with swa-cli or manual upload
- For staging: NEXT_PUBLIC_GATEWAY_URL=https://feelr-gateway-staging.feelr.workers.dev
- For production: NEXT_PUBLIC_GATEWAY_URL=https://api.feelr.dev
- Require SWA deployment token as env var or argument

**scripts/deploy-docs.sh:**
- Purpose: Deploy docs to Azure SWA
- Accept `--env staging|production` argument (default: staging)
- Steps: pnpm install -> turbo build --filter=@feelr/docs -> copy staticwebapp.config.json to out/ -> deploy
- No gateway URL injection needed (pure content site)
- Require SWA deployment token as env var or argument

**scripts/rollback-gateway.sh:**
- Purpose: Roll back gateway to a previous version
- Accept `--env staging|production` argument (required)
- Steps: list recent versions -> prompt for version ID (or accept as argument) -> confirm -> execute rollback
- Include prominent DO migration warning: "Cannot rollback across Durable Object migration boundaries"
- Use `wrangler rollback <VERSION_ID> --env <ENV> --yes --message "Manual rollback: <reason>"`

After creating all scripts, run `chmod +x scripts/*.sh` to set executable permissions. Verify permissions are set with `ls -la scripts/`.

Create `docs/deployment/SECRETS-INVENTORY.md` documenting every deployment secret. Add a prominent warning header:

```
> **WARNING:** This document catalogs secret metadata only. Never add actual secret values, API keys, or tokens to this file.
```

Organize by storage system with the following structure per secret:

**Section 1: GitHub Actions Repository Secrets** (org: progradetech, repo: feelr)

1. CLOUDFLARE_API_TOKEN
   - What: Cloudflare API token with Workers, KV, and D1 edit permissions
   - Where stored: GitHub Actions repository secret
   - Used by: gateway.yml (staging + production deploys), ci.yml (gateway-preview)
   - Scope: Single Cloudflare account, single zone (feelr.dev)
   - Required permissions: Account > Workers Scripts > Edit, Account > Workers KV Storage > Edit, Account > D1 > Edit
   - Rotation procedure: Create new token in Cloudflare Dashboard > My Profile > API Tokens with same permissions -> `gh secret set CLOUDFLARE_API_TOKEN --body "<NEW_TOKEN>"` -> trigger staging deploy to verify -> delete old token
   - Impact if compromised: Deploy code to Workers, read/write KV and D1 data

2. CLOUDFLARE_ACCOUNT_ID
   - What: Cloudflare account identifier (not truly secret, but stored as secret for consistency)
   - Where stored: GitHub Actions repository secret
   - Used by: gateway.yml, ci.yml
   - Rotation: Cannot rotate (tied to account). If account compromised, create new Cloudflare account.
   - Impact if compromised: Low alone; combined with API token allows deployments

3. SWA_DASHBOARD_DEPLOYMENT_TOKEN
   - What: Azure Static Web Apps deployment token for feelr-dashboard
   - Where stored: GitHub Actions repository secret
   - Used by: dashboard.yml (staging + production deploys)
   - Retrieval: `az staticwebapp secrets list --name feelr-dashboard --query "properties.apiKey" -o tsv`
   - Rotation: `az staticwebapp secrets reset-api-key --name feelr-dashboard --resource-group feelr-rg` -> retrieve new token -> `gh secret set SWA_DASHBOARD_DEPLOYMENT_TOKEN`
   - Impact if compromised: Deploy arbitrary content to dashboard SWA

4. SWA_DOCS_DEPLOYMENT_TOKEN
   - What: Azure Static Web Apps deployment token for feelr-docs
   - Where stored: GitHub Actions repository secret
   - Used by: docs.yml (staging + production deploys)
   - Retrieval: `az staticwebapp secrets list --name feelr-docs --query "properties.apiKey" -o tsv`
   - Rotation: Same as dashboard token but for feelr-docs
   - Impact if compromised: Deploy arbitrary content to docs SWA

5. HOMEBREW_TAP_GITHUB_TOKEN
   - What: GitHub Personal Access Token (classic) with `repo` scope for andrewprograde/homebrew-tap
   - Where stored: GitHub Actions repository secret
   - Used by: release.yml (GoReleaser pushes Homebrew formula)
   - Rotation: Generate new PAT at github.com/settings/tokens -> `gh secret set HOMEBREW_TAP_GITHUB_TOKEN` -> tag a new release to verify
   - Impact if compromised: Push arbitrary Homebrew formulas to tap repo

6. GITHUB_TOKEN
   - What: Automatic GitHub Actions token (provided by GitHub, not manually set)
   - Where stored: Auto-generated per workflow run
   - Used by: All workflows (PR comments, releases, SWA repo_token)
   - Rotation: Automatic (new token per run, expires after workflow)
   - Impact: Scoped to repository, permissions defined in workflow YAML

**Section 2: Cloudflare Worker Secrets** (set per-env via `npx wrangler secret put`)

For each of these, document both staging and production as separate entries:

1. ENCRYPTION_KEY (staging + production)
   - What: AES-256-GCM encryption key for stored credentials in auth vault
   - Where stored: Cloudflare Worker secret (per-environment)
   - Used by: Gateway encrypt/decrypt operations
   - Generate: `openssl rand -base64 32`
   - Rotation: Generate new key -> `npx wrangler secret put ENCRYPTION_KEY --env <ENV>` -> **WARNING: existing encrypted credentials become unreadable; must re-store all connector credentials after rotation**
   - Impact if compromised: Decrypt all stored OAuth tokens and API keys

2. ADMIN_TOKEN (staging + production)
   - What: Bearer token for admin API endpoints (key management, credential management)
   - Where stored: Cloudflare Worker secret (per-environment)
   - Used by: Dashboard authentication, admin API routes
   - Generate: `openssl rand -hex 32`
   - Rotation: Generate new token -> `npx wrangler secret put ADMIN_TOKEN --env <ENV>` -> update dashboard login
   - Impact if compromised: Full admin access to key and credential management

3. SLACK_CLIENT_ID + SLACK_CLIENT_SECRET (staging + production)
   - What: Slack OAuth app credentials
   - Where stored: Cloudflare Worker secret (per-environment)
   - Used by: Slack OAuth flow
   - Rotation: Regenerate in Slack API dashboard -> update both Worker secrets
   - Impact if compromised: Impersonate Feelr Slack app

4. STRIPE_SECRET_KEY + STRIPE_WEBHOOK_SECRET (production only, optional)
   - What: Stripe API key and webhook signature verification secret
   - Where stored: Cloudflare Worker secret (production environment only)
   - Used by: Billing and usage metering
   - Rotation: Roll key in Stripe Dashboard > Developers > API keys -> update Worker secret -> update webhook secret in Stripe Dashboard > Webhooks
   - Impact if compromised: Access to billing data, ability to create charges
